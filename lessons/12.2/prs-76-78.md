# Pull requests (#76, #77, #78)

## PR #76: Production build: restore point, migrate, verify every migration applied

- **Merge commit:** `743b95b` (2026-11-18T15:14:44Z)

## Summary

Drizzle's migrator skips any migration older than the newest one already applied and still prints success. Two branches that each generate a migration can merge in the wrong order, and the older migration then never runs on production. The build's migrate step becomes **restore point, migrate, verify**:

```diff
 migrateDatabase (vercel buildCommand → npm run db:migrate)
   take advisory lock
+  if production and a migration is pending
+    print LSN, time and the Neon restore command   # no secret; restoring stays a person's call
   migrate                                          # as today
+  missingMigrations(journal vs drizzle.__drizzle_migrations)
+    any missing → fail the build, naming them       # every build, previews included
```

```diff
 src/db/
+├── migration-journal.ts   # readJournal, journalOutOfOrder, missingMigrations (exported for #65)
 └── migrate.ts             # migrateAndVerify: the step above
```

`journalOutOfOrder` runs in `npm test` and fails when the journal's timestamps don't strictly increase. That catches the out-of-order merge at PR time.

A separate commit fixes the glossary lint. It banned `restore`, `deploy` and `release` in names because each is listed under another word's _Avoid_, even though all three are glossary terms. An _Avoid_ entry that is itself a term is now left to review. Other avoided words such as `netBalance` are still caught.

Refs #73. The ticket stays open for its last check: the restore point has to be seen in a real production build log on the first production migration.

## Evidence

- **Before:** on a database migrated with the journal minus `0004`, a full migrate skips `0004_expense_foreign_amounts` and prints `Migrations applied.`
  **After:** `migrateAndVerify` rejects with `Migrations not applied: 0004_expense_foreign_amounts. …` (test: *the build's migrate step › refuses, naming the migration, when one was skipped…*)
- Local Postgres, `VERCEL_ENV=production`, scratch database:
  ```text
  Restore point before migrating production (pending: 0000_skeleton, …, 0006_settlement_foreign_amounts)
    LSN:  0/137D41C8
    Time: 2026-11-18T14:47:53.199Z
  To restore production's root branch to this point (a person's call, only within Neon's ~6-hour history), run:
    neon branches restore production ^self@0/137D41C8 --preserve-under-name production_before_20261118_144753
  Migrations applied and verified.
  ```
  A second run, with nothing pending, prints only `Migrations applied and verified.`
- The full suite passes: 318 tests, plus typecheck and lint.

## Merge Danger

**Door:** one-way. The PR changes what runs migrations (`src/db/migrate.ts`, `scripts/migrate.mts`). It adds no migration, but it changes the migration runner, so it's left for a human to merge, not auto-merged.

**Blast Radius:** deploys

Every build, previews included, now fails if any journal migration isn't recorded as applied. That is the intent, but a database whose migration history was edited by hand would block deploys until it's fixed. The printed Neon command has no `--project-id`, so it relies on the operator's CLI pointing at Potluck's project.

## Summary

The contract half of dropping `app_info`. #74 stopped reading and writing it; this removes the definition and drops the table.

```diff
 drizzle/
 ├── 0006_settlement_foreign_amounts.sql
+├── 0007_drop_app_info.sql     # DROP TABLE "app_info";
 src/db/
-└── schema.ts: appInfo         # the walking-skeleton table, marked deprecated in #77
```

- The migration drops only `app_info` and its check `app_info_single_row`. The 0007 snapshot differs from 0006 by that table alone.

- `migrate.test.ts`'s "passes on a database migrated in order" held back the hard-coded `0006` to leave one migration pending; with 0007 present that skipped an older migration. It now holds back the newest one in the journal, so the next migration won't break it.

This goes against spec #1's "migrations only add" on purpose: the table has been unused since #74 and held only the walking skeleton's greeting.

## Evidence

  **After:** on this worktree's database, `npm run db:migrate` prints `Migrations applied and verified.` and `to_regclass('public.app_info')` is `null`. `npm run check`: 22 files, 315 tests pass.
